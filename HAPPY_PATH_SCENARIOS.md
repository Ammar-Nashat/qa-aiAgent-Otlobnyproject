# Atlobni Merchant Dashboard — Happy Path Scenarios (QA Handoff)

**Scope:** Merchant Dashboard only (`designforge-ui.com/Atlobni`). No scenario in this document was executed through the Customer App, Driver App, or Admin panel — those require separate access and separate test coverage.

**How to read Execution Status:**
- **PASS** — an actual Playwright execution in this session produced evidence the scenario works.
- **FAIL** — an actual execution confirmed the scenario is broken.
- **NOT TESTED** — documented from the SRS/discovery but never executed.
- **NEEDS CLARIFICATION** — the SRS and discovery don't give enough information to define correct expected behavior.

Documenting a scenario is not the same as testing it. Only rows with a specific test file, script, or logged evidence below are PASS/FAIL; everything else is NOT TESTED even if the underlying screen/button was seen during discovery.

Known bugs are listed separately in the **Known Bugs** section at the end, not mixed into the happy-path rows below (the one exception is the Has Offer filter, which is itself a happy-path scenario that was executed and failed).

## Known Bugs (kept separate from the happy-path table above)

1. **Has Offer filter under-returns products** (see PRD-09 above, the one exception documented in-table because it was directly executed and failed). `GET /products?has_offer=1` omits at least one product correctly linked to a currently active, multi-product offer — confirmed against real, week-old merchant data, not just fresh QA data. Not a test-setup or UI-rendering issue; confirmed via direct API inspection.
2. **Offer image field mislabeled optional** — the "صورة العرض" field shows no required-field indicator, but submission is blocked server-side ("مطلوب صورة واحدة للعرض على الأقل") without one.
3. **Product logo field mislabeled optional** (store onboarding) — same pattern as #2: labeled "(اختياري)" but submission blocked without a file.
4. **Offer create response reports a stale/incorrect status** — `POST /offers` returns `offer_status:"disabled"` with an untranslated i18n key (`"messages.disabled"`) for an offer whose dates cover "now," while the very next `GET /offers` list call correctly reports the same offer as `"active"/"نشط"`. The UI matches the (correct) list endpoint, so this is confined to the create response itself.
5. **Untranslated i18n key on offer product-chip removal** — the "remove product" button's accessible label renders as the raw key `offers.products.remove` instead of localized text.
6. **Deleting a product linked to an active offer is not blocked** (relates to SRS gap G4) — confirmed business rule says this must be prevented with a clear message; already reported to the business/dev team and marked **KNOWN BUG — PENDING FIX**. Destructive testing of this exact scenario has not been executed, per instruction, pending approval.
7. **No merchant account-recovery / support-contact flow on login or a blocked-account screen** (SRS gap G6) — already reported and marked **KNOWN BUG — PENDING FIX**. The mechanism for changing a registered phone number remains a separate, unresolved business clarification (see ACC-01).

## Explicit Scope Disclaimer

No scenario above — PASS, FAIL, or otherwise — reflects execution through the **Customer App**, **Driver App**, or **Admin panel**. All PASS/FAIL results in this document come exclusively from Playwright runs against the Merchant Dashboard in this session (`tests/products/*.spec.ts`, `tests/e2e/*.spec.ts`, and ad-hoc registration scripts). Any customer- or driver-facing behavior implied by an SRS requirement (e.g., what a customer actually sees when a product goes unavailable, or driver order-assignment logic) is marked NOT TESTED or NEEDS CLARIFICATION here and requires separate test coverage with the appropriate app access.
